# TURN 中继服务选型（S3c-c-preflight，2026-08-05）

> 上游：设计稿 `docs/superpowers/specs/2026-07-31-storage-architecture-design.md`
> `:1057`（仅 10–20% 连接走中继）、`:1073`（用托管服务）、`:1077`（可见元数据风险）。

## 1. 背景

STUN 直连约 80–90%（对称型 NAT 打不通），TURN 兜底后接近 99%。DTLS 握手在两个 peer
之间完成，TURN 只转发已加密的 UDP 包，**连密钥交换都参与不了**。因此托管 TURN 在隐私上
不构成降级，与自建 coturn 安全性相同。

两条诚实的限制（`:1077`）：
1. TURN 可见元数据 —— IP 地址、包大小、传输时序
2. 信令通道完整性是前提 —— 被攻破的信令可替换 DTLS 指纹实施中间人

## 3. 判据

### 3.1 可见元数据风险（`:1077`）

三家都可见 IP、包大小、时序（TURN 协议本身不可免）。**差异在 IP 暴露粒度**：

- **Cloudflare Calls**：全球 200+ 城市边缘，IP 暴露到城市级。对攻击者而言，
  「这两个 IP 在旧金山传了 200MB」比「这两个 IP 在 US-West 传了 200MB」更精确。
  但 Cloudflare 的边缘节点数量多，每个节点承载的连接数远多于单区域服务器，
  单连接在其中难以被单独识别。

- **Twilio**：~20 个区域，IP 暴露到区域级。粒度较粗，但区域少意味着每个区域
  承载的连接数更多，单连接在其中更难被单独识别。

- **Xirsys**：~12 个数据中心，IP 暴露粒度与 Twilio 相当。但自有数据中心不如
  云厂商的全球分布，某些地区可能没有就近节点（延迟上升）。

**结论：三家元数据风险同级，无实质性差异。** TURN 的元数据暴露是协议本身的性质，
不是供应商的选择。哪天真要消除元数据风险，只能靠自建 TURN（coturn）+ 完全控制的
网络路径，而不是换供应商。

### 3.2 成本（`:1057` 仅 10–20% 连接走中继）

| 场景 | Cloudflare Calls | Twilio | Xirsys |
|---|---|---|---|
| 100 设备，月均各传 5GB，10% 中继 | 免费 | ~$20 | 免费 |
| 1000 设备，月均各传 5GB，10% 中继 | 免费（1TB 内） | ~$200 | 超出免费层，~$50 |
| 1000 设备，月均各传 20GB，10% 中继 | 超出免费层，~$80 | ~$800 | ~$200 |

### 3.3 凭证时效性

**三家都发短期 credential，不是常量字符串。** 这是 `IceServerProvider` 端口设计
的基础——它必须是一个能随时返回当前有效凭证的异步接口，而不是一个静态配置。

## 4. 建议

**首选 Cloudflare Calls**，理由：
1. 免费层覆盖 100 设备 × 5GB/月 × 10% 中继的典型场景，零成本起步
2. 全球边缘节点最多，延迟最低
3. 供应商锁定最低（TURN 标准协议，换供应商只需换 token 签发 URL）

**备选 Twilio**，理由：
1. 有客户端 SDK（取 token 更快上手）
2. 区域可选（合规需求）

**不选 Xirsys**，理由：
1. 无公开 SLA
2. 节点数最少，部分地区延迟高
3. 免费层最小（500MB/月），容易超

## 5. 与本项目的关系

| 本轮做 | 本轮不做 |
|---|---|
| 选型文档（本文件） | 部署、签约、填密钥 |
| `IceServerProvider` 端口签名（P3） | 任何供应商 SDK 集成 |
| 端口上加「凭证有时效」的语义 | 真 TURN token 签发逻辑 |

**端口设计（见 P3）**：`IceServerProvider` 返回 `Future<List<IceServer>>`，
其中 `IceServer` 含 `urls`、`username`、`credential` 字段，且 `credential`
是 `Future<String>` 而非 `String`——表明它可能是运行时获取的短期凭证。
