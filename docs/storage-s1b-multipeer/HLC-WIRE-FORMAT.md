# HLC 线上格式规格（HLC-WIRE-FORMAT）

> 本规格由 ACT 08 钉死（TASK_DETAIL.hlc_wire_format_spec），ACT 11 产出为
> 语言中立文档 + 黄金用例。任何实现（Dart / Rust / Web / 其它）都必须
> 逐条对齐，否则同一份数据会被两端读成不同的版本坐标。
>
> 版本：S1b（crdt ^5.1.3 的 Hlc 类）

## 打包布局

版本坐标打包成 **signed int64**（8 字节）：

```
packed = (l << 16) | c
```

- `l` 占**高 48 位**：HLC 的物理分量，单位是 **UTC 毫秒**（`dateTime.millisecondsSinceEpoch`）。
- `c` 占**低 16 位**：HLC 的逻辑计数（counter），取值 `0..65535`。
- 字节序：**大端（Big-Endian）**，即 `packed` 的最高字节排最前。
- 空值：版本坐标缺失用「无戳」表示，【不得】用 0 冒充 —— 0 是一个合法且最小的戳。

## 决胜规则

比较两个版本坐标时：

1. 先比 `l`（大者胜）；
2. `l` 相等时比 `c`（大者胜）；
3. `l` 与 `c` 都相等时比 `deviceId` 的 **UTF-8 字节序**（无符号逐字节字典序，大者胜）。
   **不是 UTF-16 码元序、不是本地化排序。**
   - Dart 的 `String.compareTo` 是 UTF-16 码元序，对 BMP 外字符与 UTF-8 字节序
     结论【相反】，跨语言实现必须统一到 UTF-8 字节序。
   - 例：U+E000 的 UTF-8 首字节 0xEE，U+10000 的 UTF-8 首字节 0xF0，
     故 U+E000 < U+10000（UTF-8 序）；而 UTF-16 序下恰好相反。
4. 若 `l`、`c`、`deviceId` 三者全部相等，视为【同一个版本】（identical）。

## 时钟漂移阈值

- 漂移上限：**60,000 毫秒（1 分钟）**。
- 含义：本地时钟相对远端墙钟（或 merge 时的 wallTime）偏差超过 60 秒时，
  时钟实现必须【拒绝】该次操作（抛异常），不得静默接受。
- 各语言实现必须用同一个值，否则一端接受、另一端拒绝，同步分叉。

## 溢出行为与有效范围

- `c` 达到 65535：下一次自增必须【回卷并推进 l】（`c=0, l+=1`），
  或按实现策略在 c 满时抛溢出错误 —— 但【不得】静默截断 c。
- `l` 的有效上限：打包值落在 **signed int64** 里，最高位是符号位，
  因此合法范围是 **`0 <= l < 2^47`**。`l >= 2^47` 时 packed 变负、比较结果翻转。
  - 2026-08-02 实测：当前毫秒数 `l ≈ 2^40`，打包后占 57 位，距符号位还有 6 位；
    需要 `l >= 2^47`（约公元 6440 年）才会变负 —— 实践安全，但必须写死上限。
  - 实现遇到 `l >= 2^47` 时：**拒绝并报错**，不许静默截断。
- deviceId 的比较基准是 **UTF-8 字节序**（见决胜规则第 3 条）。

## 黄金用例

以下各组 `(l, c, deviceId)` → `packed(hex)` → 与另一组的比较结果，供
Rust / Web 客户端对表验证实现正确。

### 打包向量

| l                | c     | deviceId          | packed（hex，64 位补零） |
|------------------|-------|-------------------|--------------------------|
| 0                | 0     | device-a          | `0000000000000000`       |
| 1                | 0     | device-a          | `0000000000010000`       |
| 1                | 1     | device-a          | `0000000000010001`       |
| 1700000000000    | 0     | device-a          | `018bcfe568000000`       |
| 1700000000000    | 65535 | device-a          | `018bcfe56800ffff`       |
| 1700000000001    | 0     | device-a          | `018bcfe568010000`       |
| 1700000000000    | 0     | device-\u{e000}   | `018bcfe568000000`       |
| 1700000000000    | 0     | device-\u{10000}  | `018bcfe568000000`       |

### 比较向量

设 `A = (1700000000000, 0, device-a)`、`B = (1700000000000, 65535, device-a)`、
`C = (1700000000001, 0, device-a)`、
`Ue = (1700000000000, 0, device-\u{e000})`、
`U1 = (1700000000000, 0, device-\u{10000})`：

| 比较        | 结果 | 理由                                   |
|-------------|------|----------------------------------------|
| A vs B      | A < B | l 相同，c 小者小（c 低位不被吃掉）     |
| B vs C      | B < C | l 递增胜出                             |
| A vs A      | A = A | 自反                                   |
| Ue vs U1    | Ue < U1 | deviceId 按 UTF-8 字节序：EE < F0 |
| U1 vs Ue    | U1 > Ue | 反对称                                 |

### Hlc 串格式（本地持久化 / 日志）

除 int64 打包外，Hlc 还有一个规格化字符串形式（`Hlc.toString()` / `Hlc.parse()`），
用于本地时钟持久化与诊断日志：

```
<ISO8601 UTC 毫秒>-<counter 4 位大写十六进制补零>-<nodeId>
```

例：`2026-08-03T12:34:56.789Z-000F-device-a`

- `counter` 以 16 进制大写、4 位补零输出（`0x0000..0xFFFF`）。
- `nodeId` 即 `deviceId`（设备标识）。
- 该串格式与 int64 打包是同一 Hlc 的两种编码；跨语言传输一律用 int64。
